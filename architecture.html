lendisk architecture · v0.10

The chosen architecture as of 2026-10-30, as described in DESIGN.md v0.10: the v0.9 drawing with every part that REQUIREMENTS does not ask for removed. versitygw is still embedded as the S3 front end over a lendisk decorator, and the store is still versitygw's posix backend on a local directory or its s3 backend against any S3 service the user names. What changed: one store serves both roles, so a friend's buckets live wherever your own do, posix or Garage alike; replication is an in-process S3 client that dials friends through tailcat directly, so there is no rclone child, no rc socket and no loopback forwards; the object hash is taken from the write stream at capture, so each object is read once per replica; and the tunnel has one port. One process, one binary.

Status: DESIGN.md v0.10 describes this drawing, and REQUIREMENTS v0.9 made the two changes it needed: EP-16 admits a store behind an S3 service the user names, with EP-12, COMPAT-4, SEC-3 and scenarios 1 and 7 extended to match, and REPL-10 was reworded for a hash taken at capture. The parts dropped from v0.9, rclone as the transfer engine and non-S3 replica targets, sit behind the same replica interface and remain v1.1 candidates.

What the picture encodes

  • versitygw is the S3 front end, in-process. It owns the loopback listener, parses every request, verifies every SigV4 signature including restic's and Kopia's aws-chunked streaming form, and implements multipart, listings, versioning and object lock. lendisk supplies an IAMService and writes no protocol code. embedgw takes listener addresses, not a net.Listener, so the loopback listener is versitygw's own and the tunnel side goes through a lendisk bridge. Unchanged from v0.9.
  • The tunnel has one port and the bridge is where peer identity is enforced. lendisk accepts each tailcat connection, learns its peer key, and checks the relationship on every request. Requests under /_lendisk/ are the control API and are answered by lendisk; no S3 bucket can have that name, since bucket names start with a letter or digit. Every other request is an S3 request, passed on to versitygw's internal unix socket only if its access key is the peer key, with the signed headers untouched (SEC-10 to SEC-15). One listener, one middleware, one hostile-peer harness target.
  • Credentials are resolved by lendisk, never stored by versitygw. On loopback the IAMService returns the per-bucket key from lendisk.db. For a borrower it derives the per-pair secret from the two node keys on demand (NET-7a), and only when a relationship exists. Unchanged from v0.9.
  • The decorator is the one lendisk seam, and it hashes at capture. It implements versitygw's backend.Backend interface and wraps the one real backend. For your buckets it records a pending queue row, wraps the write stream in a SHA-256 as it passes to the backend, makes the call, marks the row done with the hash, and turns a not-found into a read-through from a replica. EP-11 needs the hash at write time anyway, to notice a changed acknowledged key, so taking it here costs no extra read. For borrowers' buckets it applies the allow-list, quota, hash verification, immutability and retention. Capture is in-process and crash-safe exactly as in v0.7 (EP-3).
  • One backend per node, serving both roles. The user picks backend/posix or backend/s3 at init, and the node's own buckets and every borrower's lent-* bucket go into the same store. On a disk, they are sibling directories. On a Garage, they are sibling buckets. This is what every household in figure 2 already did in v0.9; making it the rule removes the mux between two backend instances and gate Q-W. A friend who wants lent buckets on a second disk mounts it at the bucket directory (gate below).
  • The capability profile is declared for tested stores and probed for the rest. The POSIX backend has versioning, object lock, checksum verification and conditional writes natively. Behind backend/s3 those depend on the upstream. Garage, RustFS and B2 are tested, so their profiles ship as data and the probes at init and store set confirm them; for any other store the probes decide. status labels the weaker modes, as S3-4 already does for external replicas.
  • Replication is an S3 client in the process. The worker takes the next object from a replica's FIFO queue, reads it through the decorator, and uploads it with minio-go, with the SHA-256 from the queue row as x-amz-meta-lendisk-sha256 and as the request checksum where the target verifies one. Multipart with per-part progress on the queue row gives resume at part granularity (REPL-6). A token-bucket limiter and a time-of-day timetable in lendisk give REPL-7. minio-go was chosen on 2026-10-30 for its fit with S3-compatible stores; its owner risk (D11) is accepted, and if the library is withdrawn a new decision is taken, with the AWS SDK for Go v2 as the obvious replacement behind the same interface. For a friend, the client's HTTP transport dials through the tailcat Client, so there is no loopback forward, no child process, no rc socket and no second binary. The lender-only profile simply has no queue.
  • A lender can lend space it does not own. Point the one store at a B2 bucket through backend/s3 and lend part of it; quota, immutability and retention are still the decorator's. The borrower never holds a credential to it. Unchanged from v0.9.

Four friends, four configurations

The same binary in four households, each using a different corner of the design. Lending is pairwise and one-way; the arrows are replication flows from a borrower to the lender holding its copy. Carla and Björn have no relationship and never learn of each other. Every household keeps its own buckets and its friends' buckets in the same store.

What the four exercise

  • Every store kind at once, one per node. Plain files (Anna, Carla), an S3 server the user already runs (Björn), a provider as the store (Dag), and a provider as an external replica (Anna's B2). Three declared store profiles, one backend per node, no mux.
  • Every retention mode. Store-enforced through object lock on plain files (Anna, Carla), store-enforced through versioning and lifecycle at a provider (Dag, and Anna's B2 with a key that cannot delete), and client-side tombstones where the store has none (Björn). status on each borrower shows which it got.
  • Lending space you do not own. Dag's lent buckets are a prefix in a bucket he pays for. Björn's quota, immutability and retention are enforced by Dag's daemon, and Björn never holds the Hetzner credential.
  • Pairwise trust (P-2). Anna and Björn are mutual, two invites. Every other pair is one-way. Carla and Björn share no relationship and appear nowhere in each other's state, even though both hold data for Anna and one of them holds data for Dag.
  • Every network case. Hole-punched (Anna to Carla), relayed through DERP because of CGNAT (Anna to Björn, shown as such in both nodes' status), and a static public address dialled directly (everyone to Dag). In every case the borrower's S3 client dials through its own tailcat Client; nothing listens on loopback for replication.
  • Evict mode in the wild. Björn's 300 GB of photos keep about 10 GB locally; a restore reads packs through from Anna or Dag. Anna, holding Björn's packs, cannot read them (P-3) and cannot delete them early (RET-2).
  • Recovery for each. Anna rebuilds from her phrase and Carla's address. Dag rebuilds from his phrase and Anna's address, and his manifest brings back the Hetzner credential. Carla has nothing to recover: her store is readable with restic -r /mnt/usb/lendisk/lent-anna-laptop on any machine, with nothing running.

The capability profile

Applies to a store behind backend/s3. For a tested store (Garage, RustFS, B2) the profile ships as data and the probes confirm it at init and store set; for any other store the probes decide it. Recorded in lendisk.db, shown in status. The POSIX backend has every row natively. An external replica is checked for two things only: whether versioning is on (S3-4) and whether the credential can delete (S3-5).

Five ways back to your data

  1. Normal. restic restore against 127.0.0.1:9000; the store serves it, read-through fills any gap.
  2. From a friend, directly. lendisk peer forward B 127.0.0.1:9100, then restic against that port; B's embedded gateway serves B's store.
  3. After total loss. lendisk recover with the phrase and one lender's address; the manifest brings back peers, buckets, and the credentials of the store and every external replica.
  4. With no lendisk at all. On the default store, restic -r <dir>/laptop on the plain files, on your disk or on the lender's. Behind backend/s3, any S3 client with the store's credential.
  5. From a disk in the post. lendisk export on either side writes the tool's own layout; restic -r /mnt/usb/laptop opens it.

Open gates

  • The decorator can see the authenticated account (Q-I.2). Config.IAMService taking lendisk's implementation is confirmed; whether the account reaches the backend call is not. Fallback: a vendored patch carried as a Go module replace. Unchanged.
  • backend/s3 pass-through (Q-V). Multipart and checksums are documented; whether versioning, object lock and conditional headers pass to the upstream unchanged is not, nor whether buckets can live as prefixes in one upstream bucket, as figure 2 draws for Dag. Unchanged.
  • backend.Backend churn. Five versitygw minor releases in four months, no stability statement. Pinned and vendored, one file touches it, CI runs restic and Kopia end to end on every bump. Unchanged.
  • Listing at 500k objects on the POSIX backend and Object Lock semantics on it (Q-X). Unchanged.
  • New: the in-process replica client (replaces Q-U). Multipart upload with per-part progress on the queue row, resumed after a restart; a token-bucket limiter and the time-of-day timetable (REPL-7); memory per concurrent transfer against OPS-7 on a Pi 4 (G-3); a friend's 507, 403 and 412 reaching the worker through the tailcat transport. All measurable in the two-node CI setup. If REPL-6's byte-offset resume or REPL-7's timetable turn out larger than expected, rclone behind the same interface is the v1.1 answer, as D12 says.
  • New: lent buckets on a second disk under one posix root. A lender who wants friends' data on another disk mounts or links it at the bucket directory. This needs versitygw's temp directory and versioning directory to stay on the same filesystem as the bucket, or its temp-then-rename and version moves cross a mount. If they do not, the fallback is two posix roots and the mux comes back for that case only.
  • Resolved: hash at capture. REQUIREMENTS v0.9 reworded REPL-10 so the hash may be taken when the backup tool writes the object, as long as the replica verifies the bytes it receives against it.
  • Resolved: the requirement changes (Q-T). REQUIREMENTS v0.9 added EP-16 for a store behind an S3 service the user names, extended EP-12, EP-15, LEND-6, COMPAT-4 and scenarios 1 and 7 to match, and put the store credential in SEC-3.
