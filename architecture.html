lendisk architecture

From SPEC.md draft v0.5 (2026-10-27). One Go daemon per node. Every node is a borrower of its friends' disks and a lender of its own, in the same process.

Why "backup finished" and "offsite" are two events

What the picture encodes

  • One capture point. The S3 front end (embedded versitygw) and the restic REST shim both call the same decorated backend. Nothing proxies S3. versitygw terminates SigV4 itself.
  • Crash-safe capture. The decorator writes a pending queue row before the backend call and marks it complete after. Pending rows are reconciled against the filesystem at startup.
  • Local staging. Writes land on the POSIX store at disk speed. The worker drains the SQLite queue in the background and hashes each object while sending it. A friend being offline never affects a backup.
  • Two kinds of replica, one interface. A friend's node over tailcat, or any S3 bucket over minio-go. Both count toward min_replicas, and the S3 bucket is a lendisk-free restore path.
  • Loopback in, tunnel out. S3 and REST bind 127.0.0.1 only. The node ID is the WireGuard key, so the tunnel is the authentication. Relays only see addresses and volume, and the user picks which relays may.
  • Same binary on both sides. The lender's store uses the same keys-as-paths layout, with tombstones, retention and per-peer quota. A lender can hand you a disk.

Worked example: five friends, 10 GB each, two lenders apiece

Five is the smallest group where every node borrows from exactly two others and lends to exactly two others with no pair being mutual. The per-node numbers below do not change with group size.

Disk per node

The spec's rule is to lend 1.2 times the repository size per borrower, leaving room for tombstones. R, the restic repository size, is taken as 10 GB. The lender also keeps a free-space floor on its filesystem, 5 percent by default, below which it refuses writes rather than deleting anything.

Where the bytes live

Every copy is a plain directory in restic's own layout, so no copy depends on lendisk to be read. Node A, which lends to D and E:

node A
├── <store>/<bucket>/            # A's own copy: data/ index/ snapshots/ keys/ config
│                                #   restic -r <store>/<bucket> works with the daemon stopped
├── lent/<D-id>/<bucket>/        # D's replica, same layout, reachable only with D's key
├── lent/<E-id>/<bucket>/        # E's replica
├── tombstones/                  # deleted objects, kept 30 days, no early purge
├── lendisk.db  (SQLite)         # replication queue, acked SHA-256 index, quotas, peers
└── config dir  (mode 0600)      # identity key, S3 and REST credentials
      + D's and E's encrypted node manifests (their peer lists, for recovery)

What a lender can and cannot do

  • Read contents: no. restic encrypts and authenticates every object on the borrower's machine before it leaves. The lender never has the restic password and lendisk never asks for it. A generic bucket written with plain rclone is outside this guarantee and needs an explicit opt-in flag.
  • See metadata: yes, by design. Object sizes and counts, backup timing, and the borrower's IP unless relayed. A relay sees only IPs and volume, because WireGuard is end-to-end underneath.
  • Alter or drop data silently: no. The lender checks every object against the SHA-256 the borrower sends. The borrower challenges each lender daily with a random byte range and a nonce. A failed challenge marks the replica unverified and raises an alert.
  • Reach the other replica: no. If B is compromised, B can lose or withhold A's copy at B and see A's traffic metadata. B cannot reach A's copy at C, impersonate A to C, or learn who else A deals with.
  • Read a neighbour's replica on the same disk: no. D's and E's directories on A are reachable only with their own keys.

What the borrower is protected against

  • Ransomware on its own machine. An attacker with full control can delete the local copy and queue deletes, but lenders turn deletes into tombstones for 30 days and no protocol call can purge early. The owner runs lendisk undelete from a clean machine.
  • A lender going offline. Backups continue at local disk speed. The queue persists in SQLite through days-long outages and resumes per object.
  • A lender disappearing for good. Nothing re-replicates automatically, because that would be transitive trust. The node alerts and the owner invites a new lender.
  • Losing everything. The 24-word recovery phrase rebuilds the identity, the node manifest on any one lender restores the peer list, and restic restores directly from that lender's replica. Both lenders also hold a disk you could physically collect.

Transport. All peer traffic is plain HTTP inside a WireGuard tunnel from tailcat. The node ID is the WireGuard public key, so the tunnel is the authentication, and each node accepts connections only from known peers and pending invites. The S3 and REST endpoints bind loopback only and never face the network.
