lendisk architecture · v0.12

The chosen architecture as of 2026-11-06, as described in DESIGN.md v0.14. The process is the one v0.11 drew, with less in it. A bucket asks for copies: each data object is placed on that many friends by free quota and the metadata on all of them, and the node itself re-places copies when a friend leaves or goes quiet. Every friendship is one quota that both friends lend each other, each side's own number, the smaller one in force. An external S3 bucket is an overflow target that only takes what friends cannot hold. What v0.12 took out: versitygw's versioning and object lock are off everywhere and the decorator alone keeps retention, with tombstones moved aside under .lendisk/tomb/; the store is versitygw's posix backend on a local directory, and an S3 service as the node's own store (EP-16) is post-v1; evict mode, failure domains and quota negotiation over the wire are post-v1 or gone; and lendisk owns every listener, proxying all of them to versitygw on one internal unix socket. Unchanged: versitygw embedded as the S3 front end over a lendisk decorator; one store for both roles, a friend's buckets beside your own; replication as an in-process S3 client that dials friends through tailcat directly; the object hash taken from the write stream at capture; one tunnel port. One process, one binary. v0.13, after the first spikes: the operation allow-list is a gate in front of versitygw's routing, versitygw's admin API (which cannot be left out) is made unreachable, and object lock is refused at the gate.

Status: DESIGN.md v0.12 describes this drawing, against REQUIREMENTS v0.11. That version gave up one promise on purpose: a single lender's copy is no longer a complete repository (P-5). A restore without lendisk combines the copies of any N − c + 1 places, where N is the number of places in the pool and c is copies. Non-S3 targets remain v1.1 candidates behind the same replica interface.

What the picture encodes

  • versitygw is the S3 front end, in-process, on one internal socket. It parses every request, verifies every SigV4 signature including restic's and Kopia's aws-chunked streaming form, and implements multipart and listings; its versioning is off and object lock is refused at lendisk's gate, a middleware in front of versitygw's routing that also holds the operation allow-list. lendisk supplies an IAMService and writes no protocol code. embedgw takes listener addresses, not a net.Listener, so versitygw is given <data>/run/gw.sock and nothing else: it opens no TCP port.
  • One bridge owns every listener. lendisk listens on 127.0.0.1:9000, on each [[endpoint.listen]] LAN address (TLS by default), and on the one tunnel port inside tailcat, and proxies every request unbuffered to gw.sock with the signed headers untouched. In the tunnel the bridge learns the connection's peer key, checks the relationship on every request, answers /_lendisk/ itself (the control API: redeem, challenge, manifest, quota, version, undelete, list) and passes an S3 request on only if its access key is the peer key (SEC-10 to SEC-15). On loopback and the LAN it refuses /_lendisk/ and node-ID access keys and otherwise just proxies. One code path, one hostile-peer harness target, one extra in-process hop that Q-L measures.
  • Credentials are resolved by lendisk, never stored by versitygw. On loopback the IAMService returns the per-bucket key from lendisk.db. For a borrower it derives the per-pair secret from the two node keys on demand (NET-7a), and only when a relationship exists. Unchanged from v0.9.
  • The decorator is the one lendisk seam, and it hashes at capture. It implements versitygw's backend.Backend interface and wraps the one real backend. For your buckets it records a pending queue row, wraps the write stream in a SHA-256 as it passes to the backend, makes the call, marks the row done with the hash, and turns a not-found into a read-through from a replica. EP-11 needs the hash at write time anyway, to notice a changed acknowledged key, so taking it here costs no extra read. For borrowers' buckets it applies quota, hash verification, immutability and retention; the allow-list is the gate's, because versitygw itself calls some backend methods on every request. Capture is in-process and crash-safe exactly as in v0.7 (EP-3).
  • One backend per node, serving both roles. backend/posix on the directory the user named at init; the node's own buckets and every borrower's lent-* bucket are sibling directories in it. One backend instance, no mux, gate Q-W closed. A friend who wants lent buckets on a second disk mounts it at the bucket directory (gate below). backend/s3, the same gateway re-signing to an S3 service the user already runs or pays for, is drafted in D15 and is post-v1 (EP-16).
  • Retention is the decorator's alone; store features are not used. Versioning, object lock and conditional writes in versitygw are off, and its request-checksum verification is not relied on: the decorator already hashes every stream, already checks its index before a write, and RET-2 only guards against the borrower, so a store-enforced mode would protect against nothing the requirements ask for. A borrower's delete moves the object to .lendisk/tomb/<key>/<time> in the same bucket, records a row in tombstones, hides the key from that borrower, and the purger removes it after the window. A put to a tombstoned key with the same hash is accepted and the tomb dropped; a different hash is refused (LEND-4). One path on every store, no probe, no status labels, and gate Q-I.4 closed.
  • Placement decides where each object goes; nobody names replicas. When the decorator completes a capture, the placer gives a data object copies places: the friends with the largest share of their quota still free, and an overflow target only for copies no friend can take. A metadata object (restic indexes and snapshots, Kopia index blobs) goes to every friend, but only once every earlier data object has its copies, so any N − c + 1 places together always hold a consistent repository (REPL-1). Local-only keys (restic locks/, Kopia _log) are never replicated. The placement table in lendisk.db records it, and recovery rebuilds it from each friend's list answer, which carries key, size and hash.
  • The owner's node moves copies, never the lender. When a friend is removed, fails a challenge, lowers the quota or stays unreachable for seven days, the re-placer copies its objects to the rest of the pool first and deletes them there second, so nothing drops below the copies it had. The same worker drains overflow back to friends when they gain room. A lender still never forwards (P-2, PEER-11).
  • Every friendship is one number, enforced on both sides. Each side holds its own number for the friendship (lendisk peer quota <peer> <bytes>), the control API's quota call exchanges them, and the smaller is the quota in force in both directions (P-8, LEND-8). Lowering takes effect at once; raising takes effect once both have raised. There are no proposals and no pending state: when the pool is short, status and an alert name the friend and the number that would cover it, and the two people talk.
  • Replication is an S3 client in the process. The worker takes the next object from a place's FIFO queue, reads it through the decorator, and uploads it with minio-go, with the SHA-256 from the queue row as x-amz-meta-lendisk-sha256; a single PUT also sends it as the request checksum, and each multipart part sends its own SHA-256 in an unsigned trailer (spike #4). Multipart with per-part progress on the queue row gives resume at part granularity (REPL-6). A token-bucket limiter and a time-of-day timetable in lendisk give REPL-7. minio-go was chosen on 2026-10-30 for its fit with S3-compatible stores; its owner risk (D11) is accepted, and if the library is withdrawn a new decision is taken, with the AWS SDK for Go v2 as the obvious replacement behind the same interface. For a friend, the client's HTTP transport dials through the tailcat Client, so there is no loopback forward, no child process, no rc socket and no second binary. The lender-only profile simply has no queue: it is a node with no buckets yet.
  • Post-v1: lending space you do not own. Pointing the one store at a Garage or a provider bucket through backend/s3 and lending part of it is EP-16, kept in the documents and the examples for v1.1. Evict mode (EP-9) is post-v1 for the same reason: v1 has one store kind and one storage mode.

Four friends, four configurations

The same binary in four households, each using a different corner of the design. Every line is a friendship: mutual, one quota lent in both directions, created by one invite. Nobody names replicas; each node spreads its copies over its friends by free quota. Carla and Björn have no friendship and never learn of each other. Every household keeps its own buckets and its friends' buckets in the same store.

What the four exercise

  • One store kind, four disks. Plain files on a NAS volume, a server disk, a USB disk and a VPS disk; a provider appears only as an overflow target (Anna's B2). One backend per node, no mux, no probe. Björn's Garage and Dag's Hetzner bucket as the store are the post-v1 examples (EP-16).
  • One retention mode at friends. Every lender's decorator moves a deleted object to .lendisk/tomb/ and purges it after its own window: 30 days at Anna, Björn and Dag, 60 at Carla. Only the overflow target differs: Anna's B2 keeps versions with a lifecycle rule and a key that cannot remove them (S3-4, S3-5).
  • Placement at three pool sizes. Björn has two friends at two copies, so placement degenerates to mirroring. Dag has three friends with plenty of room, so his packs are spread and any two friends hold everything. Anna's friends are full, so the placer reaches for overflow, the second choice, and status warns that her repository is above what her friends alone can protect.
  • Symmetric quotas, including the unused half. Every friendship is one number. Carla has no buckets, so the 450 GB her friends lend her back is promised but unused; status on Anna and Dag shows it, and if Carla adds a bucket nothing about the friendships changes.
  • Pairwise trust (P-2). Five friendships, five invites. Carla and Björn share no friendship and appear nowhere in each other's state, even though both hold data for Anna and Dag.
  • Every network case. Hole-punched (Anna and Carla), relayed through DERP because of CGNAT (Anna and Björn, shown as such in both nodes' status), and a static public address dialled directly (everyone to Dag). In every case the borrower's S3 client dials through its own tailcat Client; nothing listens on loopback for replication.
  • A friend leaving. If Dag left, Anna's re-placer would have nowhere to put his 150 GB but B2; Björn's photos would fall to one copy and his status would say a new friendship is needed, the only case that needs an invite (OPS-2). Nothing is lost meanwhile: Dag keeps what he held for the retention window.
  • Recovery for each. Anna rebuilds from her phrase and Carla's address; the manifest names Björn, Dag and B2, and the placement is rebuilt from each friend's list answer and a listing of B2. Dag rebuilds from his phrase and any friend's address; the manifest carries only overflow credentials (SEC-3), shown once for the environment. With nothing of lendisk running, Anna's laptop is the keys of any three of her four places copied into one directory (N − c + 1 = 3), each found under the name on her recovery sheet.

Store features the design does not use

v0.11 probed six store capabilities and labelled the weaker mode of each in status. v0.12 drops the probe: versioning and object lock are off on every bucket, the decorator's capture hash is the only integrity check, its index is the only immutability check, and retention is its tombstones on every store. The one probe that may return with the post-v1 s3 backend is a timed server-side copy, as a performance hint for tombstone moves and exports. An overflow target is still checked for two things: whether versioning is on (S3-4) and whether the credential can remove versions (S3-5).

Five ways back to your data

  1. Normal. restic restore against 127.0.0.1:9000; the store serves it, read-through fills any gap from whichever place holds the object.
  2. From friends, directly. lendisk peer forward to N − c + 1 friends, copy each replica's keys into one directory with any S3 client, then restic -r on it; each friend's embedded gateway serves its store and refuses anything outside the allow-list.
  3. After total loss. lendisk recover with the phrase and one lender's address; the manifest brings back friends, buckets, copies and the credentials of every overflow target, and each friend's list answer rebuilds the placement and the hash index. Read-through works with some friends offline, as long as every object has a reachable holder.
  4. With no lendisk at all. On the default store, restic -r <dir>/laptop on your own plain files. From the pool, the keys of any N − c + 1 places copied into one directory, from their plain files or through any S3 client; the same key always has the same bytes, so the union is the repository.
  5. From disks in the post. lendisk export on each of N − c + 1 friends, given the bucket's lent- name from your recovery sheet, writes its replica in the tool's own layout; copied together, restic -r /mnt/usb/laptop opens them.

Open gates

  • The decorator can see the authenticated account (Q-I.2). Config.IAMService taking lendisk's implementation is confirmed; whether the account reaches the backend call is not. Fallback: a vendored patch carried as a Go module replace.
  • backend.Backend churn. Five versitygw minor releases in four months, no stability statement. Pinned and vendored, one file touches it, CI runs restic and Kopia end to end on every bump.
  • Listing at 500k objects on the POSIX backend (Q-X).
  • The in-process replica client (Q-Y). Multipart resume after a restart, the limiter and timetable, memory per transfer on a Pi 4, and a friend's 507, 403 and 412 reaching the worker through the tailcat transport. rclone behind the same interface is the fallback.
  • Lent buckets on a second disk under one posix root (Q-Z). versitygw's temp directory must stay on the bucket's filesystem, and so must the decorator's .lendisk/tomb/ renames; otherwise two posix roots and a mux for that case only.
  • New: placement and re-placement parameters (Q-AA). Re-route unsent copies after an hour away, re-place sent ones after seven days, fill by free share. G-1's households show how much traffic a normal weekend away causes.
  • New: drain-back deletes at overflow targets (Q-AC). Draining needs a credential that can mark objects deleted but not remove versions. Whether B2, Wasabi, Hetzner and R2 can grant exactly that is checked per provider; where not, the user chooses.
